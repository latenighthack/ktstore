# Observation hooks for 0.2.7

`Database` and `createDatabase` accept an optional `StoreObserver`, called synchronously in the caller's coroutine with events that carry the caller's `CoroutineContext`. `Database.open()` reports the stored and target versions, a fresh or already-current database distinctly, each configured step and `MigrationScope` operation with its store or index, transformed rows and duration, schema verification, and a terminal event naming any failed step and operation. Store and transaction-scope reads, saves and deletes, `clearStores`, and scoped and logical transactions report store, index, relation kind, row counts, payload bytes, cache use, transaction membership, duration and outcome. Batched cache misses report once per backend load; lazy lists are not reported per element.

Errors are reported and rethrown unchanged, cancellation is reported as cancellation, and observer throws are discarded. Events never render keys or rows as text: bound keys are only reachable through `StoreRelation` references.

Without an observer the delegates, transactions, lazy reads, shared row cache and batched reads are unchanged and no event payloads, timings or statistics are allocated; backends discover migration observation through a coroutine context element present only on observed opens. Persisted payloads, keys, schemas and delegate transaction ownership are unchanged. The library and migration Gradle plugin versions advance together to 0.2.7.

Validation covers JVM in-memory and SQLite, IndexedDB/JS (Chromium), Android instrumentation, macOS, and iOS simulator conformance, including new observer conformance for migration sequences over the migration example (fresh, already current, upgrade from each historical baseline, failing step), every operation event and outcome, observer throws, cancellation mid-transaction, and identical delegate traffic with and without an observer. Live PostgreSQL tests were skipped (no server configured). Fullhouse consumer verification was not run.
